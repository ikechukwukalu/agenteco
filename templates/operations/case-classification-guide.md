# Case Classification Guide

## Purpose

Classify cases from investigation findings so the right team can resolve them fairly. Not every complaint is a software fault. The department implementing a correction is not automatically responsible for causing it. These categories do not define case statuses or authorize actions outside existing permissions.

| Code | Category / type | Meaning | Expected response |
| --- | --- | --- | --- |
| SD | Software Defect — Bug Issue | Software is broken or differs from approved requirements or intended existing operation. | Software investigates the technical problem and prepares an authorized fix. |
| SD | Software Defect — Usability Issue | The feature works as designed but is difficult to understand, find or use. | Business/product owner reviews and approves the improvement; Software implements the agreed update. It is not automatically a technical bug. |
| SM | Staff Misunderstanding — Knowledge Gap | Correct information, training or communication was missing, unclear or outdated. | The responsible communication, training or documentation owner supplies the explanation or updated information. Do not blame staff for unavailable guidance. |
| SM | Staff Misunderstanding — Staff Negligence | Correct instructions were available, adequately communicated and reasonably accessible, but not followed. | The relevant supervisor provides guidance and addresses repeated failures under existing procedures. Require reasonable evidence; misunderstanding alone is insufficient. |
| PD | Process Defect — Failed Process | Following the designed process does not always reach the intended outcome or leaves no clear next action. | Business owner defines and approves the missing procedure; Software implements separately authorized changes. |
| PD | Process Defect — Outdated Process | A previously correct process no longer matches changed policies or operating needs. | Responsible department communicates and approves updated requirements and agreed timing. If Software accepted the change but missed its agreed deadline, investigate that cause too; do not label it only a process defect. |
| PD | Process Defect — Incomplete Process | Important situations or customer needs were not included in the agreed requirements. | Business owner defines and approves the additional functionality. A newly identified need does not prove the original software was defective. |
| PD | Process Defect — Process Conflict | Individually valid rules or features interact to produce an unintended problem. | Business and technical owners review the clash, identify whether requirements, impact assessment or implementation caused it, and agree the correction. Link the 2A conflict record. |
| DC | Duplicate Case | The same underlying issue already has a case. | Link the newer case to the original and preserve additional evidence there; authorized staff close it as a duplicate under the product's procedures. Multiple reports can indicate wider impact. |

Compare actual behaviour with approved requirements and relevant evidence. Record uncertainty instead of guessing. A system working as designed can still embody an unsuitable business process. The purpose is effective resolution and prevention, not blame. No classification automatically authorizes implementation, disciplinary action or case closure.
