# Local-Only Agent Eco Space Mode

## Purpose and authority

Local-Only Mode governs an approved project **without installing Agent Eco files in the project's Git worktree**. It is for a user who can work in a repository but cannot or does not wish to commit Agent Eco adapters or product context to it. “Silent” means no Agent Eco footprint in that repository's tracked files; it never means concealing activity from the human user, evading employer policy, or falsely attributing AI work. Company administrators, endpoint controls, tool providers, and service logs may still observe activity. Do not promise invisibility.

This mode requires an explicit product-scoped human choice after checking the employer's AI, data-handling, intellectual-property, retention, and device rules. It does not override those rules, canonical Agent Eco safeguards, code review, implementation authorization, tests, or human-only PR merges. If permission to use an agent or store product knowledge is absent or unclear, stop the affected setup and request an approved location or policy decision. A personal account or personal remote copy is **off by default** and is never a prerequisite. Use it only after explicit permission for that destination and data classification; a company-owned project does not imply permission to export its knowledge.

## External local layout

The human selects a company-approved local context root **outside the project worktree and its Git directory**. Keep the product's context, Agent Eco cache or approved mirror, registration, pending updates, and audit history there. A local context may serve several code repositories of the same product, but keep product and access boundaries distinct. Never write `.agenteco/`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, or an Agent Eco `.gitignore` entry into the company project under this mode. Do not stage or push local Agent Eco records through the company's code repository.

Use the [local project registry](../templates/local-only-project-registry.yml) as the activation index and a separate [product registration](../templates/local-only-registration.yml) outside the worktree. The index maps approved repository identities to registration paths; it is disabled by default. The product registration records product/application identity, exact repository remote and canonical path, approved local context root, governance source version and commit, allowed tool loaders, data classification and ownership, backup/retention decision, and optional remote destination and authorization. Verify a project's remote **and** path (or an approved stable identity) before activating; a directory name or untrusted repository file alone cannot opt a project into Local-Only Mode. If a project already has governed repository adapters or a conflicting registration, report the conflict and do not silently replace them. Never publish either record if it contains confidential paths or project identity without approval.

The local context is authoritative only for this authorized Local-Only Mode, not a second canonical Agent Eco repository or a claim that other machines share it. Preserve source revisions, decisions, rule history, contract evidence, and context drift as in the central-context standard. A separately approved local Git repository can provide history and review **without adding files to the company code repository**; it is optional. If Git is disallowed, use an approved local history and backup mechanism. Do not treat a laptop's sole copy as durable. Confirm encryption, access control, backup, restore test, and retention/deletion rules with the data owner. Do not put protected `.env` or `.env.*` values, secrets, or production customer data in context.

## Session activation and verified auto-detection

The [Local-Only Startup Prompt](../templates/call-agent-eco-space-local-only.md) is the portable entry path for a new session. It names the project and authorized local context. A supported local agent may instead use the [optional user-level loader](../templates/local-only-user-loader.md) or a user-owned launcher that checks the local registry before loading the context. Keep the global instruction generic: it points to the local registry, not to company secrets or a personal cloud account. Disable cloud synchronization of instructions containing company identity unless separately approved. Support and precedence vary by tool and surface; verify the actual instruction source and context access in every new session. A hosted or cloud agent that cannot read the approved local path is **not** auto-activated and must request an approved attachment or use the manual prompt with accessible material. Do not infer support from the model name.

After activation, run a Local-Only Readiness Preflight: verify repository identity, registry and local context provenance, current accessible governance version and exact commit, context integrity and freshness, applicable specialist, active business rules and decisions, source revision, classification, access limits, and pending local updates. Report limitations to the authorized human. The standard repository manifest/adapters/outbox checks are replaced **only for this verified mode**; do not auto-repair or install repository adapters in the company worktree. If source or context is missing, enter Access-Degraded or Governance-Uncertain Mode as appropriate and stop work whose correctness depends on it.

## Local context updates and handoff

After the normal scoped implementation authorization, write product-specific context to the approved local root. Include the source commit and evidence, affected contracts and consumers, decisions, tests, FARS/2A findings where relevant, owner, timestamp, and status. Keep a local pending-update ledger and collision-resistant package identifiers so later sessions can reconcile rather than duplicate. A local write is **not** a central-context PR, human merge, remote publication, or synchronization to another machine. Never say it is.

Where a separately authorized local context Git repository exists, prepare a local branch and reviewable commit and have the authorized human accept or merge it; do not merge on the agent's behalf. Without Git, present a reviewable diff or change record and preserve the prior version using the approved history mechanism. Do not delete a pending package before its destination is verified and the human has accepted the update. If a remote context destination is later approved, deduplicate by package ID, source revision, and fingerprint, prepare a human-reviewed context PR, and retire the local pending copy only after the remote merge and ledger entry are verified. No remote destination is inferred from the company code remote or the user's personal account.

Code and implementation PRs still follow the repository's authorized workflow. Do not add Agent Eco-only files or confidential local context to those PRs. If the employer requires disclosure of AI assistance, follow that requirement; Local-Only Mode is not a license to misrepresent authorship, approvals, QA, or deployment state.
